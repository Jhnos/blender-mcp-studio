### 關節怎麼做:先例把銷拿掉了(2026-09-08 親驗)

要把指節縮到人手尺寸時先查了現成專案,結果**改變了問題**:

| 專案 | 關節做法 | 授權 | 對我們的意義 |
|---|---|---|---|
| 100_fingers | **活動鉸鏈**,無銷;OpenSCAD 參數化 `[親驗]` | GPLv3 程式 / CC BY 4.0 模型 | 銷不是必需品。<https://github.com/kg398/100_fingers> |
| RoninHand | **半原地列印**,核心三件 `[親驗]` | Apache 2.0 程式 / CC BY 4.0 機構 | 同上,且組裝更少。<https://github.com/Polymorph-Intelligence/RoninHand> |
| BiDexHand | 參數化 CAD(SolidWorks/STEP)`[轉引]` | MIT | 授權最寬,但格式進不了本管線。<https://github.com/wengmister/BiDexHand> |
| OpenBionics | 由人手量測推導參數 | — | 人體量測的參考 |

**兩個最相關的都刪掉了銷。** 而我們的尺寸瓶頸正是銷:力矩臂下限 = 銷孔/2 + 壁厚 + 腱孔/2,
這三項沒有一項隨本體縮小。

裁決:**縮小銷、拿掉軸承,不改關節型式**。理由與代價:

| 選項 | 力矩臂比值 | 代價 |
|---|---|---|
| **縮小銷、無軸承**(採用) | 1.19 → **1.76** | 公差變緊,要靠試片確認;仍需組裝 |
| 活動鉸鏈 | 更寬(斷面裡沒有銷) | **靠疲勞失效**,那是材料性質,幾何契約量不到;而且 GPLv3 只能當參考不能抄 |
| 半原地列印 | 更寬 | 間隙控制最難驗;整套契約要重寫 |

決定性的一點不是幾何而是**驗證**:活動鉸鏈的失效模式是疲勞,本專案的契約管線量的是幾何,
量不到疲勞。縮小銷則讓既有的每一道檢查原封不動繼續適用,而且**試片即將量到的正是它依賴的那些數字**。
程式碼一行都沒抄;抄的是「銷不是必需品」這個結論。

### 台架統計為什麼沒有復用(2026-09-08 補記)

這一條當初漏了復用檢查,事後補上。查到的結論:

| 選項 | 代價 |
|---|---|
| `scipy.stats.wilcoxon` | 帶進 numpy + scipy(約 100 MB),而本專案目前**零數值相依** |
| `pingouin` / `researchpy` | 同樣帶相依,且更重 |
| 純標準函式庫的現成套件 | **查無** `[親驗 2026-09-08 網搜]` |

而 `applied-statistics:experiment-statistics` 技能自己寫著「統計基元已經存在,
這個技能是**路由與交付強制層,不是新的統計**」——所以自己寫是**偏離那條指示**,不是風格選擇。

留下自己寫的理由,以及它的代價:
- **理由**:相依為零表示這份分析在任何一台裝著 Python 的機器上都跑得動(包括跑不了本專案閘門的
  Windows 機),而使用者要在印表機旁邊看數字。指數精確枚舉在 n ≤ 20 只有約 30 行。
- **代價**:手寫推論的錯誤是看不見的。補償方式是把它釘在**不需要參考表的算術事實**上
  ——同號時恰好是 `2 / 2^n`、翻一個符號證據必須嚴格變弱、平手走的是條件排列虛無分布
  (與經典表格是**不同的問題**,已在測試裡明說)。
- **若哪天要換**:換成 scipy 是純粹的替換,介面不變,測試不用改——它們斷言的是性質不是實作。

## repo 內部就有的東西(最大的一筆)

`src/core/domain/hinge_chain.py` 的 `HingePhalanxSpec` **已經是一個指節形狀的單軸連桿**:
本體 40 × 24 × 22 mm、有細長比檢查、最大關節角 ±50°、公舌／母叉單軸鉸鏈、
腱半徑 7 mm、軸承座 Ø8.1。它現在仍是活的,而且有測試(`tests/unit/core/test_hinge_chain.py`)。

**可復用的是連桿,不是串接規則。** 實測它的 `assembly_rotations_deg` 是 `(0, 90, 0, 90)`
——交替軸,對觸手對、對手指錯。V3 借連桿、換規則,詳見 [[hand-v3/03-finger]]。

只有它的**產生器**被歸檔在 `scripts/archive/model_hinge_chain.py`。
歸檔理由寫在 `scripts/archive/README.md`:**全樹零引用,不是幾何缺陷**。
同一份 README 也指定了復活的正確做法——先定義一個 `PresentationProfile`
(前綴／解析度／相機／燈光／地板),讓三支 render 變成三個 profile 常數,
**不是把 fork 搬回現行樹**。V3 照這條走。

| RUKA-v2 | MIT `[轉引]` | 活躍 | **若哪天要商業化,只有這條路可走** |
| AmazingHand | Apache-2.0 + CC BY 4.0 `[轉引]` | 活躍 | 不是腱驅動(平行連桿、每指兩節),只當 BOM／成本參考 |

**InMoov 的手指不是「單線 + 彈簧回位」** `[親驗]`。官網原文寫每指**兩條**線,
一條走上側、一條走下側;彈簧只負責手腕轉動時的線長補償
(「The springs are there only to give freedom to the length of the tendons when the
wrist rotates」)。所以使用者要的「三節單一線」與 InMoov 實作**是不同的機構**,
Track 2 不能照抄它的腱路徑。

## 外部:單腱三節怎麼依序閉合

`[轉引]` 文獻裡的機制有:各關節的**滑輪力矩臂比值**決定扭矩分配;
**扭簧勁度梯度**決定關節**接合順序**;分裂滑輪／浮動槓桿(whiffletree)差動把一個
致動器分給多個輸出;凸輪腱(變半徑)。理論基礎是 Birglen & Gosselin 2006。

**子代理搜遍 GitHub 找不到任何「三節單一腱 + 有記錄彈簧梯度」的開源 CAD。**
查無不等於不存在,但這是自己做的最強理由,也是 V3 唯一真正原創的機構部分。

實務上這是**兩個獨立旋鈕**:先調彈簧勁度比(決定順序),再調滑輪半徑(決定力量分配)。

## 授權後果

InMoov 與 Yale OpenHand 都是**非商業**授權,衍生物會繼承。目前 V3 是個人非商業專案,
所以可以用。但這代表兩件事必須做到:

1. `NOTICE` 檔記錄每一個外部來源與其授權,**這是一條機器可驗的規則**
   (見 [[hand-v3/02-requirements]] 的 VOC-3)。
2. **InMoov 的 STL 不進版控樹**。印來用,不提交。否則非商業條款會傳染給整包交付物,
   而且它進不了 spec 驅動的驗證管線——那條管線的每一道閘門都吃 spec,不吃匯入的網格。
