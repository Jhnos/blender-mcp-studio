# 00 — 框架為什麼存在、不是什麼

> 回導航 [[hand-framework]] · 相關 [[hand-v3/00-context]]、[[hand-framework/02-requirements]]、[[DEFERRALS]]

## 起點:V3 是一次性的手

V3 的產生器、契約、掌盤把借來的連桿(`HingePhalanxSpec`,銷 4 mm + MR84 軸承)的每個數字
寫死在裡面。當人手尺寸的無軸承連桿 `CompactHingeLinkSpec` 出現時,發現三件事——每一件都親驗過:

| 事實 | 出處 | 後果 |
|---|---|---|
| `build_finger` **曾**在 `phalanx_part_count != 1` 時 raise | 舊 `scripts/finger_v3_geometry.py:221-225`(M3 已刪) | 精簡連桿的全部回報值是「力矩臂能排序」(窗比 1.19 → 1.76),而產生器**建不出有梯度的手指** |
| `scripts/ci.sh` 完全不跑契約驗證器,`--real` 也沒有 | `scripts/ci.sh:57-91` | 本輪抓到十次缺陷的契約系統是**手動跑的** |
| 掌盤寫死連桿與力矩臂;`thumb_base_palmar_mm=22.0` 是絕對值,註解說上限是掌盤厚度,**沒有不變式** | `src/core/domain/palm_v3.py:44-59, 66-80` | 15 mm 深的連桿會讓拇指根凸出 7 mm 而不報錯 |

第一件說明:借來的連桿排不了三個關節,被寫成「這台機器的性質」——其實是**那根銷的性質**。
第二件說明:上層驗證最大的洞不在幾何,在**閘門沒有接進 CI**。
第三件說明:掌盤不是連桿參數化的,它只認識一種連桿。

狀態:第二件 M1 已接進 CI;第一件 M3 已由規劃層解除(每相異臂一份零件);第三件 M4 已加不變式(凸出 23 被拒,V3 的 22 由連桿推導)。

## 目標

一套**連桿參數化、規格驅動、契約驗證**的手產生器,滿足三個可證偽的宣稱:

1. 它能**逐面數、逐尺寸**重現 `models/hand-v3/`(不用 sha:STL 匯出不可位元組重現,本輪已證)。
2. 它能用精簡連桿建出**有力矩臂梯度**的手,並通過同一套契約。
3. 契約由規格**生成**,不再有任何手打的字面值。

順序是硬的:**先在 V3 上證明框架,再做任何新實例。**

## 與 hand-v3 的關係:同一台機器的下一層,不是下一版

V3 樹裡的軟層物理、介面契約、先例調查、台架協定、試片協定**全部仍然有效**,這棵樹指過去、不重寫。
V3 的印製包是這個框架的**參考答案**——重現差分拿它當母數。

## 明確不做

- 不動 `models/octopus-hand-v1|v2/`、`models/biaxial-hinge-v6/`、V1 產生器與契約、`models/hand-v3/` 的任何位元組。
- **不為無銷關節建抽象層**。先例(`100_fingers` 活動鉸鏈、`RoninHand` 原地列印)證明銷不是必需品,
  但活動鉸鏈靠疲勞失效,幾何契約量不到——為一個驗不了的東西設計介面是投機的泛化。
  寫成有觸發條件的延後:[[DEFERRALS]] D-005。
- 不發布 `models/hand-compact/`,直到使用者對渲染圖做 Lane B 驗收(D-008)。
- 不做 MDR:本案沒有 UI。
- 不碰 web / API / MCP 任何一層。
