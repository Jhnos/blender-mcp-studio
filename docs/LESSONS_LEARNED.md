## 2026-09-09

### 掃描只對目標函數負責 → 最佳解撞上沒被掃的那條閘門
- **觸發情境**:用參數掃描選設計(擺位、尺寸),目標函數是其中一個性質(可達性),而驗收閘門還量別的性質(靜止時不互穿)。
- **該主動檢查**:真機閘門量的每一個性質,離線有沒有一個(哪怕粗糙的)模型可以先算?掃描的可行域有沒有把它們都當約束?
- **為什麼沒抓到**:V3 的擺位碰巧把唯一的交叉落在關節上,所以「可達就夠」在 V3 上從來沒有被證偽。換一個實例,同一個掃法選出的最佳解在真機 19/20——差的那一項正是沒掃的。
- **如何預防**:每條真機閘門在域層配一個離線近似(`thumb_rest_clearance_mm` 對 `disjoint_groups`),進 `strict` 不變式,掃描把它當約束;真機閘門保留為 ground truth。同族:`表面成功訊號 ≠ 語意真實`。

### 靠「名字」認自己剛建的物件 → 宿主對重名加後綴,第二次起全部認錯
- **觸發情境**:在 Blender/DCC/任何會自動去重名字的宿主裡,建了物件之後用「名字等於我要的名字」判斷它是不是主體/第一個。
- **該主動檢查**:同一個名字會不會在同一場景被建第二次(第二條鏈、第二次執行)?宿主重名時做什麼——報錯、覆蓋、還是靜默加 `.001`?
- **為什麼沒抓到**:單元測試建一次就過;第一條鏈也過。第二條鏈的主體叫 `PHALANX_1.001`,判斷式落空,主體被當成「不是第一個」而落單。抓到它的是下游數場景物件的閘門(8 ≠ 3)。
- **如何預防**:身分用**引用或位置**(「這個 part_index 第一次出現」),名字只在最後指定;每個會被重複呼叫的建構函式,至少有一個測試呼叫兩次。

### 差分閘門讀的目錄裡還躺著上一次的輸出 → 產生器半路死掉,差分照樣綠
- **觸發情境**:閘門 B 讀閘門 A 寫出的檔案(`tmp/<slug>/*.stl`),A 失敗時檔案不會消失。
- **該主動檢查**:A 失敗了,B 讀到的是什麼?有沒有任何機制讓「A 沒寫」與「A 寫了」在 B 眼裡不同?
- **為什麼沒抓到**:B 只看檔案內容,而上一次成功的檔案內容當然是對的。本案 A 的匯出剛好在 raise 之前,所以這次沒被騙,但那是運氣。
- **如何預防**:產生器一開始就刪掉自己上一次的全部輸出;差分對「缺檔」是 FAIL 不是 skip(已有)。同族:`表面成功訊號 ≠ 語意真實`。

### 常駐程序的「要重載哪些模組」清單是手打的 → 漏掉的模組靜默跑舊碼,驗證照樣綠
- **觸發情境**:驗證在一個**常駐**的直譯器/程序裡重跑程式(Blender、Jupyter、長駐 worker),靠一份 `reload_modules` 之類的清單讓它吃到新碼。
- **該主動檢查**:清單是**推導**出來的還是手打的?有沒有一個檢查把清單和實際的 import 閉包逐一比對?新模組加進來時,誰會發現它不在清單上?
- **為什麼沒抓到**:漏掉的模組不會報錯——它只是用上一次載入的那份碼,而上一次的碼多半也能跑完並回報綠。本案 13 個手打名字漏了 import 圖裡 5 個,其中一個(`finger_link`)正是這一輪新建、擁有幾何決策的模組。
- **如何預防**:清單由讀原始碼(AST,不能 import——頂層 `import bpy`)推導 import 閉包生成,葉子在前;一個靜態測試拿簽入的清單對閉包比對,缺一個就紅。**推導器自己也會漏**:`from pkg import name` 要解析成子模組檔,列成 `pkg` 只會重載 `__init__`——第一次出現這種 import 就列錯了,靠 `build_hand_contracts --check` 的 diff 看出不對。同族:`表面成功訊號 ≠ 語意真實`——「跑完了」不等於「跑的是新碼」。

### 追溯矩陣的 ref 存在,但它驗的不是那一列的性質
- **觸發情境**:矩陣要求每個 `Verified-by` ref 在 repo 裡找得到,而某列引用了一個**大而籠統**的測試檔名(如 `test_architecture_ssot`)。
- **該主動檢查**:那個檔裡**真的有**一個斷言在驗這一列說的事嗎?還是只是「檔名聽起來像」?
- **為什麼沒抓到**:ref 解析守衛只檢查字串存在。DS-1「域層不匯入 bpy」引用了架構測試檔,而那個檔裡連一個 `bpy` 都沒出現。
- **如何預防**:ref 盡量指到**測試函式名**而不是檔名;新增一列時親眼開那個測試看它的斷言。建守衛時附一個 should-fire(植入一個 `from mathutils import Vector`)證明它真的會咬。

## 2026-09-08

### 每個自由度單獨掃過都乾淨,不等於「動起來」乾淨
- **觸發情境**:多自由度機構(手指鏈、機械臂、連桿)的干涉驗證,而檢查是「一次動一個關節,掃過它的全行程」。
- **該主動檢查**:有沒有一條檢查是**所有自由度同時動**的?兩個關節各彎一半,會到達任一個單獨都不會去的位置——那個位置有沒有人看過?
- **為什麼沒抓到**:V3 的單指合約有 `joint_sweep`,把一個關節掃過 ±50° 十一個角度、全 0 重疊,綠了很久。它證明的是**每條弧各自乾淨**,而 PS-2 要的是「手指閉得起來」,那是另一句話。矩陣裡那一列(`closure_order_from_sweep_samples`)一直掛著 TODO,而且我連續好幾輪把它歸類成「等實體」——它完全不需要實體。
- **如何預防**:①軌跡要**整條一起掃**,而且用**設計預測的那條**(這裡是彈簧梯度算出來的:基節領先、遠節 0.625),這樣同一條檢查同時驗了幾何與那個預測;②新閘門上線先**餵一個已知會紅的輸入**——這條把行程從 50° 改成 200°,第 4 步起回報 365–806 對重疊,證明它有牙,不是掃過空氣;③附帶收穫:探針順便量出真正的極限(75° 才開始自碰,設計上限 50°,1.5 倍餘裕),而那是原本的單關節掃掠問不出來的。

### 修好一個缺陷時把零件扯成兩塊,而每一道閘門都看不到「它是不是一整塊」
- **觸發情境**:布林運算堆出來的零件,某個特徵(耳片、凸台、接頭)的位置由某個參數決定,而那個參數被改動。
- **該主動檢查**:改完之後,這個零件**還是一整塊嗎**?水密、非流形、面數、碰撞、尺寸——這五項**沒有一項看得到殼數**。
- **為什麼沒抓到**:V3 的公舌片是一個光禿禿的圓盤,直接放在關節中心;母叉那邊有一段頸子把耳片接回本體,公端**從來沒有**。當關節中心從 24 推到 27 mm(那是為了修「相鄰件互相侵入 2.5 mm」),圓盤跟著移走、本體留在原地,兩者相距 **0.5 mm**——而 0.5 mm 正是那次修正引入的間隙。從此每一個指節都是**兩個各自水密的實體**。合約 19/19 全過:兩個殼都水密、都零非流形、相鄰重疊 0(比以前更成立)、面數與當時記錄的一致。**是使用者看渲染圖發現的**,這是本輪第三次。
- **如何預防**:①把「一個零件 = 幾個實體」做成契約宣告(`expected_shells_per_object`),fail-closed;②新閘門上線先確認覆蓋範圍——我第一版只數了 `object_prefix` 那一組,十五個指節裡涵蓋三個、掌盤零個,是一個和模型一樣大的覆蓋洞;③**修 A 之後要重驗 A 以外的性質**:那次修正只重驗了「相鄰件不重疊」,而它破壞的是別的東西;④成對的特徵(公/母、左/右)要對照著讀——一邊有頸子另一邊沒有,是可以用眼睛看出來的不對稱。

### 追溯矩陣的 ref 是**死連結**,而檢查器只驗格式所以永遠說綠
- **觸發情境**:任何有 `Verified-by`／`Covered-by`／`Test:` 欄位的需求表、控制計畫、覆蓋矩陣。
- **該主動檢查**:把那一欄的每個 ref **拿去 grep 一次**。它是 repo 裡真的找得到的字串嗎(測試函式名、契約證據名、檔名),還是一個當初順手寫下的描述性代號?
- **為什麼沒抓到**:hand-v3 的矩陣有 22 個 ref,**21 個在 repo 裡不存在**——`test_moment_arm_gradient_monotonic`、`print_layout_within_bed`、`geometry_probe_cuff_and_port`…全是代號。而 `trace_check.py` 從頭到尾回報「all 22 requirement(s) traced」,因為 R1–R6 驗的是 `tier:ref` 的**形狀**,不是 ref 指得到東西。更糟的是其中一個 ref 指向的性質**已經被設計推翻**:ES-2 寫「力矩臂單調遞減」並標 PASS,而力矩臂早就改成相等(5.5/4.0 會讓壁厚只剩 1.85/0.35 mm,低於 2.4 最小值),為的是十五個指節共用一個零件號。
- **如何預防**:①ref 一律用**字面可解析**的名字,並加一條守衛去 grep 它們;②還沒建的檢查用 `TODO_` 前綴**留在表上看得見**,並加第二條守衛確保 `TODO_` 的名字**沒有**在程式碼裡出現(否則名字被回收、表又開始說謊,只是換個方向);③**格式對的死連結比沒有連結更糟**——它看起來是安全的;④上游檢查器說綠不代表它檢查了你以為的那件事,先讀它到底驗什麼。

### 兩個獨立算式各自產生一個位置,湊在一起就是沒人做過的決定
- **觸發情境**:同一個零件上兩個特徵的位置分別寫在不同函式裡,各自從別的量推導。
- **該主動檢查**:它們的相對關係**有名字嗎**?還是只是兩個式子算出來剛好差多少?
- **為什麼沒抓到**:進氣口的高度是產生器裡的 `-plate_height * 0.72`,袖口夾溝是另一個函式裡的 `-plate_height + body_length / 2`,算出來 −50.4 與 −50.0。進氣口半徑 3.0,所以那個 Ø6 貫穿孔**正好穿過 3 mm 厚的袖口夾帶中央**——那一圈的唯一工作就是把手套袖口壓在連續材料上。兩個數字都沒被審過,它們差 0.4 mm 是算術不是決定。同時規格導出的 `air_port_center_mm` 第二個分量**被產生器丟掉**(`_ = port_y`),而單元測試正在斷言那個被丟掉的值。
- **如何預防**:①位置關係要在規格裡**有名字**(這裡是 `air_port_clearance_mm`)並帶不變式,產生器只准讀;②看到 `_ = x` 這種「取出來又丟掉」的行,當成紅旗查;③斷言要打在**真正決定結果的那個量**上——斷言一個沒人使用的值,測試會綠而幾何不會照做。

### 「任兩者不干涉」這種宣稱,被逐對檢查漏掉的永遠是**跨群組**那一對
- **觸發情境**:一個組件由多個群組構成(五根手指、多排佈局、多個模組),而檢查是「每個群組內部相鄰兩兩比對」。
- **該主動檢查**:文件宣稱的是「群組內」還是「任兩者」?**跨群組那些配對是誰在量?** 特別是那個在幾何上會橫越其他群組的成員。
- **為什麼沒抓到**:hand-v3 的契約碰撞群組只比同一指內的相鄰節;readiness 的 `intersections` 只掃佈局盤不掃組裝好的手;四指間距是解析式的「節距 > 本體寬」而**拇指不在那條式子裡**。而拇指正是唯一橫越指列的那一根。README 卻寫著「任兩指之間靜止零干涉」。這是本專案第二次被同一個形狀咬到——列印佈局那次也是**非相鄰**的兩列重疊,只有 readiness 的 `intersections` 看得到。
- **如何預防**:①「任兩者」的宣稱要有**全配對**的證據,不能用相鄰配對頂替;②在契約層做成宣告(`disjoint_groups`),fail-closed:宣告了卻量不到就是 FAIL;③配對的鍵用**排序後**的正規形式,別讓宣告順序變成隱藏格式;④群組是空的要回報 `None` 而不是 0——空群組的「零重疊」讀起來跟乾淨一模一樣;⑤發現這件事的是**看圖**:拇指在渲染圖上橫越指列,量測才證明那是投影而非碰撞。圖不能當證據,但**圖很會提問題**。

### 宣告的母數寫著一個不存在的前綴,而那一行的存在意義就是防止空母數
- **觸發情境**:追溯矩陣／驗證計畫寫 `Population:`,用前綴、時間窗或帳號規則描述母數。
- **該主動檢查**:那個前綴/規則**現在真的匹配得到東西嗎**?拿它去 grep 一次程式碼,不要只讀文件。
- **為什麼沒抓到**:五份 V3 文件的母數都寫 `HH_V3_`,而產生器從第一個 commit 就用 `HJ_`——而且是**刻意**改的(預設 `HH_` 與既有模型撞名,害產生器清不掉自己的輸出,那本身已經是一條教訓)。於是「防止空母數」的那一行自己宣告了一個空母數,而且沒有任何東西比對過文件的前綴與程式的前綴。
- **如何預防**:母數宣告要有機器檢查——從程式碼把前綴 regex 出來,斷言文件寫的就是它,並斷言文件裡不存在其他同形狀的前綴(只斷言「有正確的」會漏掉「同時還留著錯的」)。

### `bound_box` 是快取,`data.transform()` 不會讓它失效——而閘門就靠它通過了
- **觸發情境**:在 Blender 裡量物體的世界尺寸/佔地,尤其是擺位被**烘進網格頂點**(而不是留在 object transform)的物件。
- **該主動檢查**:量的是 `obj.bound_box` 還是真的頂點?這個網格有沒有被 `data.transform()` 就地改過?有沒有**第二條獨立路徑**量同一件事,兩者對不對得起來?
- **為什麼沒抓到**:剛加的 `layout_fits_bed` 閘門用 `bound_box` 量佈局盤,回報 140.0 × 103.5... 實際是 `[140.0, 44.0]`,而真值是 242.0 × 103.5——它讀到的是掌盤**平躺前**的自己的框。閘門**PASS**。這比沒有閘門更糟:它把「沒人量過」變成「量過了,綠的」。同一份 readiness 報告用外掛的路徑量同樣四件物體,寫著 242.0 × 103.5,兩個數字在同一個 JSON 裡並排卻沒有任何東西比對它們。
- **如何預防**:①量幾何一律走 `obj.matrix_world @ vertex.co`,不要用 `bound_box`(同族陷阱:`hide_viewport` 會把物件踢出 depsgraph,本檔已有一條);②**一個量測抓不到自己量錯對象**——判準要求兩條獨立路徑的量測**互相同意**才採信,不同意就 FAIL(這正是 `表面成功訊號 ≠ 語意真實` 那條的「獨立 oracle」在幾何上的樣子);③新閘門第一次上線,要**餵一個已知會紅的輸入**確認它真的會紅,不要只看它變綠。

### 產生器不是位元組可重現的,所以雜湊不能當回歸判準
- **觸發情境**:想用「重跑產生器 → 比對 sha256」證明某次重構沒有改到幾何。
- **該主動檢查**:**同樣的程式碼連跑兩次**,產出的位元組相同嗎?先確認這件事,再拿雜湊去比對任何東西。
- **為什麼沒抓到**:重構 `palm_v3`(把旋轉基元搬出去)之後重跑,四個 STL 有三個雜湊不同,面數與尺寸卻完全一樣;而唯一**沒變**的偏偏是我改到的掌盤。形狀不對。跑第二次才發現:同樣的程式碼自己跟自己也對不起來——指節/單指/整手每次都不同,掌盤才穩定。這與本專案已記的「PNG 位元組不可重現」是同一族,只是這次發生在 STL。
- **如何預防**:①這類包的回歸判準用**面數 + 尺寸 + 契約**,不用雜湊;②manifest 裡的 sha256 是「出貨這份位元組的完整性校驗」,**不是可重現性宣稱**,文件不要讓人誤讀成後者;③任何「A 與 B 不同 ⇒ 有問題」的推論,先跑 A 兩次。

### 散文會描述產物,而閘門只驗產物——每一份拷貝停在不同的 commit
- **觸發情境**:交付物旁邊有 README、規格文件、追溯矩陣或程式註解,裡面引用了尺寸、零件數、量測結果這類**會隨修正而變**的數字。
- **該主動檢查**:文件裡每一個數字,是**從規格或位元組推導出來的**,還是某次手打之後就凍在那裡?尤其是**使用者在動手之前唯一會讀的那一份**。
- **為什麼沒抓到**:hand-v3 連續兩次修正(膝節抬高 13.5 mm、四節降三節)都只改了幾何,`models/hand-v3/README.md` 仍寫著十九個零件、90.0 mm 掌盤、319.5 mm 整手、18.2 mm 對指距離。**每一道機器閘門都是綠的**——網格水密、契約 15/15、包測試從位元組反推節數全過——因為它們驗的是網格,沒有任何東西驗描述網格的句子。更能說明這是一個**類別**而不是一次疏忽的是:同一個數字在三份文件裡有**三個不同的年份**(README 18.2、追溯矩陣與任務檔 17.6、真值 20.7)——散文被往前抄,每一份拷貝在不同的 commit 停止追蹤。
- **如何預防**:①把文件表格的數字當**斷言**驗:用穩定的**標籤**(`| 對指後最近距離 |`)定位那一列,再跟規格屬性或 STL 量測比對,這樣數字再變一次檢查仍然有效——用數字本身定位就會在第一次修正後失效;②守衛漏掉的那一格要**把守衛加寬**,不要只補數字(這次「拇指平放 29.9」躲過了第一版檢查,因為它落在句子的第二行);③**理由也會過期,不只是數字**:拇指當初被砍短是為了不追過四節手指,整手降到三節後兩者鏈長相同,結論沒變但理由換了,而程式註解還在講舊理由;④CHANGELOG 是歷史紀錄,**不要改**——只改宣稱「現況」的文件。

### `git reset --hard` 會安靜吃掉發布產物,而發布產物天生就是未提交的
- **觸發情境**:跨機器同步時用 `reset --hard` 對齊,而那台機器上剛跑完「產生 → 發布」還沒提交。
- **該主動檢查**:那台機器上有沒有未提交的**產物**?發布流程是「先寫進工作區、後提交」,所以它在提交之前永遠是 dirty 的。同步前先 `stash -u`,或先提交再同步。
- **為什麼沒抓到**:hand-v3 重新發布成三節版之後,我在 Mac 上用 `git reset --hard synced-main` 對齊(前幾次都有 stash,這次漏了),把三節的 STL 洗回四節。**包測試抓到了**:「the assembled finger holds 4 phalanges」。這是這個專案第二次被同步機制吃掉成果(第一次是 scp 帶進 CRLF)。
- **如何預防**:①同步前一律 `git stash -u`,或把「發布 → 提交」做成同一個不可分割的步驟;②包測試要能從**位元組本身**推回設計意圖(這裡是從兩個 STL 反推指節數),那條檢查在寫下的當天就抓到了這件事;③注意這條檢查如果寫成「比例 ÷ 比例」會失效——四節版的 bbox 比與「量錯對象」的比值相同,兩種病長得一模一樣。

### 內部自洽的檢查對「整體尺度錯了」完全免疫——要有一個來自設計之外的比較對象
- **觸發情境**:任何有「應該長得像某個真實東西」的設計(擬人、仿生、符合人因)。
- **該主動檢查**:有沒有**任何一條**檢查是拿設計去比外面的東西?可達性、碰撞、掃掠、水密、間隙——**這些全部是尺度不變的**:把整個設計等比放大,每一條照樣綠。
- **為什麼沒抓到**:V3 的規格叫 `AnthropomorphicPalmSpec`,而裡面**沒有一條人體比例檢查**。實際出貨的是一隻 320 mm 的手:手指 168.5 mm(人約 100)、指掌比 1.6(人是 1.0)、每指四節(人是三節)且四節等長(人是遞減)。十幾道量測閘門全綠。**使用者看一眼圖就問「你看過圖嗎」。**
- **如何預防**:①凡是「要像某個東西」的設計,加一條跟那個東西比的比例斷言,界限放寬沒關係——目的是抓「大一倍」不是抓公釐;②名字裡宣稱的性質(anthropomorphic)要有對應的檢查,否則那只是個名字;③**人看圖是有效的驗證層**,而且它抓的正好是內部檢查全盲的那一類。

### 交付的 `.blend` 不是渲染圖——渲染是過濾過的視圖,檔案是全部
- **觸發情境**:產生器同時建「要交付的東西」與「中途用的鷹架」(單獨匯出用的複本、排版用的複本),然後存成一個 `.blend` 當交付物。
- **該主動檢查**:**打開這個檔會看到什麼?** 直接列出 `hide_viewport == False` 的物件,不要看渲染圖——渲染用 `hide_render` 一次只顯示一組,所以它永遠是乾淨的。
- **為什麼沒抓到**:V3 的 `.blend` 打開會看到 25 個物件:19 節組裝好的手、**一根散裝手指插在手掌正中間**、掌盤、渲染地板。三張渲染圖全都正常,因為 `capture()` 過濾掉了。使用者打開檔案才說「跟 BLEND 開的圖不一樣」。
- **如何預防**:①存檔前把非交付物件隱藏,並加一條閘門斷言「可見物件集合 == 交付物集合」;②清理要排在**渲染之後**,因為渲染會自己建地板與燈;③不要在 `run_generator` 的前綴之外刪物件——它在 `finally` 還原可見性時會撞到已刪除的參考。

### 把物件的位置寫死在 transform 裡再交給別人擺,等於把它的位置交出去了
- **觸發情境**:一個建構函式回傳物件,而物件的一部分位置資訊留在**物件 transform**(不是網格頂點)裡;呼叫端接著設 `matrix_world` 去擺位。
- **該主動檢查**:回傳前把 transform 烤進網格,讓物件的原點就是它的參考點。或者:呼叫端用**相乘**而不是**覆寫**。
- **為什麼沒抓到**:`create_box` 會 apply scale 與 rotation,但**刻意不 apply location**——盒子的中心高度留在 transform 裡。掌盤的指根用它建,原點因此在 13.5 mm 高;擺位時 `_place` 覆寫了 `matrix_world`,整組指根就**整體下沉 13.5 mm**。掌盤頂端停在 20.0,而手指的叉孔在 27.0。**水密、一個殼、兩份契約全綠、就緒檢查乾淨——而這隻手組不起來。** 是一個只看圖的盲判評審抓到的:「每根手指最下面的叉停在它的耳片上方,中間看得到背景」。
- **如何預防**:①建構函式回傳前把位置烤進網格,原點歸零;②組裝完加一條「配合面必須到得了對方」的閘(這裡是量掌盤頂端高度,便宜且決定性);③**盲判看圖是有效的驗證層**,它抓得到所有幾何量都自洽、但東西根本裝不起來的那一類。

### 乾淨的起始場景會藏住「沒有清乾淨」這個 bug——本機永遠是乾淨的,真機不是
- **觸發情境**:產生器在一個**長時間存活**的執行環境裡重複執行(本專案是一直開著的 Blender)。本機驗證卻總是用 `--factory-startup`,每次都從空場景開始。
- **該主動檢查**:新產生器用的**命名前綴**,和清理函式**預設**清的前綴,是不是同一個?以及:在**同一個 session 裡連跑兩次**,結果一不一樣。
- **為什麼沒抓到**:`run_generator` 的預設前綴是 `HH_`(既有產生器都用它),V3 用 `HJ_`。於是 `clear_previous` 一個東西都沒刪,真機上每跑一次就疊一整隻手上去——契約量到 **9 個佈局零件而不是 5**,其中兩對重疊 196／203 個面,就緒檢查回報 `intersections`。本機用 `--factory-startup` 跑一百次也不會出現,因為場景每次都是空的。
- **如何預防**:①產生器結束前自己數一次「我剛做出來的每一種東西各有幾個」,數不對就 raise——**它比契約更早知道**;②「同一 session 連跑兩次」要當成一條例行驗證;③新增產生器時,前綴要當成參數明確傳,不要吃預設值。

### 靠物件 transform 擺位的東西,可能存檔後就不見了——擺位要烤進網格
- **觸發情境**:用 `matrix_world` / `location` 擺放複製出來的物件,然後存 `.blend` 當交付物。
- **該主動檢查**:**重新開啟存好的檔**再量一次。行程內的每一次檢查都可能是對的,而檔案裡是錯的。
- **為什麼沒抓到**:V3 的列印佈局用 transform 擺開五個零件。行程內量:正確。存檔前最後一行印出來:正確(-190.50 … 154.00)。**重新開啟同一個檔:全部是 0**,五個零件疊在同一點。改用 `location`/`rotation_euler` 直接設也一樣。最後把擺位**烤進每個複本自己的網格頂點**才穩定——頂點座標不會在存檔往返裡消失。
- **如何預防**:①凡是「要交付的 `.blend`」,驗證一律**重新開檔**再量,不要信行程內的讀值;②純呈現用的複本可以各自擁有網格並把 transform 烤進去,代價只是幾份重複網格,換到的是位置不可能遺失;③真正要共用網格的是**列印零件**,那條路徑要另外驗。

### 只比對「相鄰」的碰撞檢查,對不相鄰的那幾對是全盲的
- **觸發情境**:一組物件排在一起,用「相鄰兩兩比對」確認沒有互相穿透。本專案的 contract oracle 就明寫著它比的是相鄰(numeric-name order)。
- **該主動檢查**:排列如果會**換行／分組／繞圈**,索引上的相鄰就不等於空間上的相鄰。要嘛比**全部配對**,要嘛用一個不管相鄰性的獨立訊號(這裡是就緒檢查的 `intersections`)。
- **為什麼沒抓到**:列印佈局換行之後,重疊的是 2-5、3-5、4-5 這三對——**沒有一對是相鄰的**。我的探針與 contract 的碰撞群都回報乾淨,只有就緒檢查的 `intersections` 翻紅。兩個檢查覆蓋面不同,救回來的是覆蓋面比較廣的那個。
- **如何預防**:①相鄰式檢查要在文件裡寫明它的盲區(本專案已寫,而我還是踩了);②會換行的排列一律加一條全配對斷言;③保留一個**不同機制**的獨立檢查,不要讓所有閘門都用同一種比法。

### 「排得下」和「排在一起沒有重疊」是兩個問題,而且都要量
- **觸發情境**:產生列印佈局(print plate)。
- **該主動檢查**:**相鄰件重疊數**要是 0,**而且**整體佔地要小於床身。兩者都不能靠看圖。
- **為什麼沒抓到**:第一版用固定節距排列,對 24 mm 的指節是對的,而 140 mm 的掌盤直接穿過鄰居——實測相鄰重疊 846/846/846/422 個面。改成照各自寬度排開之後不重疊了,但變成一列 413.5 mm,**放不進 256 mm 的床**。要照床身換行,最後 182.5 × 100.5 mm 一盤放得下。
- **如何預防**:佈局產生器要把床身當參數並自己換行;驗收要同時斷言「相鄰重疊為 0」與「佔地 ≤ 床身」,少一條就會出一種看起來很像成功的失敗。

### 水密性看不見「分離的第二塊」——分離的實體本身就是完美水密的
- **觸發情境**:用 boolean union 把一堆特徵併進一個本體。任何一個特徵若沒有真的碰到本體,union 會安靜地把它變成同一個 mesh 裡的**第二個殼**。
- **該主動檢查**:數**連通殼數**,不要只數非流形邊。一個列印件如果是兩個殼,那它就是兩個零件。
- **為什麼沒抓到**:V3 拇指根被放在 x=-71,而掌板只到 -57——它是浮在旁邊的。實測:**兩個殼**,小的那個 88 個面、x 從 -82.8 到 -56.1,與掌板毫無連接。而它**非流形邊是 0、完全水密**,因為分離的實體確實是水密的。它會當成一個小零件從列印床上掉下來。修法是加一塊 thenar 凸台把它接回去(人手在同一個位置也長了一塊,理由一樣)。
- **如何預防**:①產生器加一道「殼數必須是 1」的閘;②「特徵放得離本體太遠」這個 class 要由一條有名字的推導量擋住(這裡是懸伸長度),而不是靠目視。

### 射線說「通了」可能只是那裡什麼都沒有——先驗母數,再驗宣稱
- **觸發情境**:用射線驗證孔/通道是否貫通。
- **該主動檢查**:先確認**那個位置真的有材料**,再問它有沒有被鑽通。空氣永遠是「通的」。
- **為什麼沒抓到**:同一次量測裡,我的探針回報「五條腱道 5/5 全通」,但拇指那條的 x 座標根本在掌板之外——射線穿過的是空氣。那條 PASS 與真正鑽通的四條在輸出上長得一模一樣。
- **如何預防**:射線類的驗證一律先做一次**旁證取樣**(在孔邊上打一條,必須被擋),擋得住才代表這裡有東西;擋不住就標 vacuous,**永遠不併入 pass**。

### 「這個零件合法」與「這一串零件裝得起來」是兩個問題,規格通常只檢查前者
- **觸發情境**:一個規格描述**單一可重複零件**,而成品是把它疊/排/繞成一串。
- **該主動檢查**:把相鄰兩件的**實際佔位區間**攤開比一次。特別注意「從中心突出去」的特徵(耳片、凸緣、接頭)——它們的伸出量通常不在任何一條既有不變式裡。
- **為什麼沒抓到**:V3 指節沿用的連桿把關節中心放在 24 mm、耳片半徑 6.5,所以耳片伸到 30.5;而下一節的本體(節距 48、本體長 40)從 28 就開始了——**兩個分開列印的零件在靜止姿態就互相穿透 2.5 mm**。借來的規格允許這件事,因為它自己那條規則只要求「關節中心要越過本體中心」,對「一個節距外的鄰居」完全沒有意見。而寫出這個排列的產生器**被歸檔時從來沒有契約驗過它**。實測:三對相鄰件各重疊 303／302／302 個面。
- **如何預防**:①把「相鄰件間隙」做成一個有名字的推導量並加 raise,不要只驗單件;②復用任何**未被驗證過**的既有設計時,先對它跑一次現行的驗收,不要假設它當初是對的——歸檔的理由若是「零引用」,那就代表它從來沒被驗過;③靜止姿態的碰撞與掃掠碰撞要分開量,前者更容易被忽略,因為大家都急著去驗運動。

### 鑽孔的長度要照「最後那個形狀」算,不是照它被建立時的那個形狀
- **觸發情境**:程序化建模裡先建本體、再union一些凸出的特徵、然後鑽貫穿孔。孔的深度若是從本體尺寸推出來的,就會停在特徵之前。
- **該主動檢查**:這支鑽頭要穿過的**最終**外形有多長?用零件的完整包絡去算,不要用它某個中間狀態。另外:**孔要在特徵 union 之後才鑽**,否則後面的 union 會把孔填回去。
- **為什麼沒抓到**:V3 指節的腱孔深度寫成 `body_length + 6`(46 mm),但公舌凸耳的圓心在 z=+24、半徑 6.5,整個零件實際有 61 mm。孔在 z=±23 就停了,於是腱要通過的那一段是實心的。**包絡完全看不出來**(bbox 仍是 24×22×61)、水密、零非流形——只有沿孔軸打一條射線才看得見。而且這是**同一個 class 第二次**:`octopus_tip_geometry._open_cable_paths` 的註解早就寫著「The drill has to clear the cap, not the disc」,那次是中央通道在 z=13 就變盲孔而蓋頂在 z=18。
- **如何預防**:①孔深一律由零件的完整包絡推導,並在幾何模組裡把那個推導寫成一行有名字的算式;②凡是「鑽孔 + union 凸出特徵」的組合,鑽孔排在最後;③驗收要用**沿孔軸的射線**,尺寸與水密性對這個 class 全盲。

### 拿一個自己就不穩定的東西當基準,「有差異」不帶任何資訊
- **觸發情境**:重構前後比對產出物,想證明「行為沒變」。特別是產出物包含算繪圖、
  含時間戳的容器格式、或任何非決定性的編碼。
- **該主動檢查**:**先用同一份程式跑兩次**,看基準自己穩不穩。基準不穩,
  「前後不同」就完全不是證據,而它看起來跟真的迴歸一模一樣。
- **為什麼沒抓到**:重構 `setup_render` 之後,V6 的九張 PNG 全部雜湊改變,
  我差一點就宣告重構弄壞了算繪。實測:**同一份程式連續跑兩次,九張 PNG 的雜湊同樣全部不同**
  ——Blender 的 workbench 輸出根本不是逐位元組可重現的。同一次比對裡的 STL 則四個檔全部
  位元組相同,那才是有效訊號。`.blend` 也會變,而且會多出一個 `.blend1` 備份。
- **如何預防**:①換一個確定性的 oracle——這裡改成建完場景後把 `scene` 讀回來,
  逐項比對解析度、背景色、曲率、相機位置與正交尺度、三盞燈的能量/尺寸/位置(16 項全 OK);
  ②把「舊值」釘在一個單元測試裡,再證明新程式套用的就是那組值,兩段接起來才是完整證明;
  ③挑 oracle 時先問「這個量對同樣的輸入會不會給同樣的答案」。


### 改了參數不等於改了讀它的程式：規格測試對「消費端沒跟上」全盲
- **觸發情境**：把一個常數提升成規格欄位／property，然後改它的值，期待下游幾何跟著動。
- **該主動檢查**：新欄位有沒有**真的被讀**？搜尋消費端，然後**量成品**，不要只斷言規格。規格測試問的是「這份規格自洽嗎」，不是「產出來的東西長對了嗎」。
- **為什麼沒抓到**：端蓋 facet 數改成 8、相位 property 加好、domain 測試全綠——而 `create_cap` 的 `angle = 2πi/n` 從頭到尾沒讀相位，建出來的網格四個抓取方向仍全部落在角上。整條鏈只有射線量測看得見。（順帶一課：用 heredoc 餵給 `python` 的檔案編輯，若那個 `python` 是個什麼都不做的殼，會安靜地不改任何東西——編輯後要驗檔案內容，不要信「腳本印了 done」。）
- **如何預防**：① 對「規格 → 幾何」這種鏈，驗收斷言要落在**產出物**上；② 把它做成生成器裡的閘，每次建都跑，而不是一條只在測試裡活著的紀律。

### 掃法向找「最平的面」不是射線：藏在後面的孔壁會替你回答
- **觸發情境**：想確認「某方向看過去是不是一個平面」，於是遍歷所有多邊形法向找最對齊的那個。
- **該主動檢查**：這個掃描能看到**被遮住**的面嗎？能的話它回答的就不是你問的問題。任何新寫的閘都要用「故意弄壞的輸入」證明它會紅，否則它只是一行昂貴的註解。
- **為什麼沒抓到**：中央通道與纜線孔都用 24 段圓柱鑽出，孔壁法向每 15° 一個，對任何航向都能提供半度內的對齊。把成品網格故意轉半個面(22.5°)之後，法向掃描**照樣放行**；換成從外面打一條射線、只看第一個命中面，立刻紅。
- **如何預防**：① 問「表面長怎樣」就用射線，別用集合掃描——遮蔽是問題的一部分；② 閘寫完先跑鑑別力測試（好的輸入過、壞的輸入紅），兩邊都要看到。

### 可見性有三個旗標，還原兩個等於沒還原
- **觸發情境**：任何「暫時放寬狀態、做事、再還原」的包裝，尤其是產出檔案的那種。
- **該主動檢查**：這個狀態總共有幾個開關？把它們**列出來**，不要憑印象數。還有：這個包裝寫出來的檔案，有沒有一個「空但合法」的形狀？有的話它就會安靜地通過所有存在性檢查。

- **如何預防**：① 把檢查放在瓶頸點——匯出後讀回三角面數，為零就 raise，讓這個 class 不可能再靜默；② 「檔案存在且非零位元組」對二進位格式不是有效的成功訊號，要驗它的內容計數；③ 跨版本／跨平台重生成既有交付物，是發現這類漏洞最便宜的方法。

### 兩個推導量剛好相等，就是一顆等著爆的退化布林
- **觸發情境**：程序化建模裡，一個特徵的尺寸由公式算出，而它與另一個既有面的位置**恰好**相同——通常是某個角度剛好 45°、某個比例剛好 1:1 造成的。
- **該主動檢查**：把兩邊的公式攤開，問「它們會不會在預設值下相等」。相等就是相切而非相交，布林解不出來。
- **為什麼沒抓到**：`tip_cap_flare_mm = 3.0` 讓端蓋外擴的 run 等於 rise，斜角正好 45°，於是端蓋半徑在切頂平面上正好等於圓盤半徑 18.000，表面擦過被切開的外緣邊。下一個布林在端蓋 facet 角落開出 12 條邊界邊，四個腱孔鑽下去變成 204 條非流形邊。實測：3.0 → 18.000 → 12 條；3.5 → 17.889 → 0 條；4.0 → 17.800 → 0 條。**V1 沒事純屬運氣**——它的對角墊剛好把六個 facet 角中的四個埋進實體，墊一移到正交方位，運氣就用完了。
- **如何預防**：① 這類「恰好相等」要當成不變式擋住（本輪加了「端蓋在切頂平面不得擦到外緣」的 raise）；② 靠既有配置僥倖繞開的缺陷不算修好，它只是還沒被觸發——換一個看似無關的參數就會現形；③ 追這種問題要逐步驟量 boundary／non-manifold 邊數，第一個變壞的步驟才是根因，之後的都是連鎖。

### 一片有寬度的東西，它的餘裕不能只在中心線上量
- **觸發情境**：判斷某個**有角度跨度**的特徵（墊、肋、扇形面）會不會撞到別的東西。
- **該主動檢查**：這個特徵跨多少度？障礙物在那整段跨度上的伸展是變動的嗎？要取跨度內的**最大值**，不是特徵中心那一條線上的值。
- **為什麼沒抓到**：本輪寫了 `hardware_reach_on_a_cardinal_mm`，只量正交方位那一條線得到 16.70 mm，判定墊（內面 17.2 mm）安全。但墊跨 ±25°，而母根腳的角落在 **68.7°、半徑 17.92 mm**，正落在朝向 90° 那片墊的跨度內——墊其實與根腳重疊。這與 2026-09-06「拿『面』的距離當包絡」是同一個 class，**在已經寫下並引用過那條教訓之後又犯了一次**。
- **如何預防**：① 任何 clearance 屬性的 docstring 要寫明「在哪個角度量的」，寫不出來就是量錯了；② 更根本地，這種幾何斷言要拿真實網格去掃，不要拿代表性數字推——本輪最後正是靠 2×2 交叉實驗（方位 × 剖面）才把真因釘死，前兩個由推理得出的假設都被自己的實驗推翻。

### `slots=True` 的 dataclass 上，零參數 `super()` 是壞的
- **觸發情境**：用 `@dataclass(frozen=True, slots=True)` 做版本子類、覆寫父類的 property 又想沿用父類的值。
- **該主動檢查**：這個類別有 `slots=True` 嗎？有的話 `super()` 不能省略參數。
- **為什麼沒抓到**：`slots=True` 會讓 decorator 回傳一個**新的類別**，方法裡隱含的 `__class__` cell 仍指向裝飾前那個，於是零參數 `super()` 丟 `TypeError`。實測：`Child().value` 炸掉，`Child2` 用 `super(Child2, self)` 正常回 9.0。
- **如何預防**：① 顯式寫 `super(Cls, self)`，並在原地留一行「不要簡化回去」，否則下一個讀到的人會把它改壞；② 這個 repo 的 spec 全是 frozen slots dataclass，V2 又開了子類化先例，所以這條會再遇到。

### 同一個 class 踩第三次，就不該再靠紀律，要在瓶頸點設閘門
- **觸發情境**：某個失效 class 已經寫進教訓、也知道怎麼避免，但它又發生了——通常是因為那個「避免方法」是一條要每次記得遵守的規則。

- **為什麼沒抓到**：紀律型的預防在「當下想得到」時有效，在「趕著做別的事」時無效。Blender 的 `hide_viewport` 讓 Boolean 靜默失效這件事，同一個工作階段內踩了三次——指尖特徵、掌盤裁切、coupon 裁切——而且第二、三次都發生在剛把這條教訓寫進檔案之後。更早的證據一直在那裡：`hinge_retention` 在 boolean 前後手動切換可見性，那正是前人踩過同一個坑、各自記得的痕跡。

### 拿「面」的距離當包絡，量到的是最近點不是最遠點
- **觸發情境**：用一個代表性尺寸（外徑、寬度、標稱半徑）去做間距／干涉判斷，而該物件不是圓——有平面、有角、有凸出。
- **該主動檢查**：這個尺寸是物件的**最遠點**，還是某個代表點？從軸心量到每一個頂點取最大值，不要用命名裡的那個數字。任何「加大接觸面」的變更，都要同時問它把包絡撐大多少。
- **為什麼沒抓到**：Ø42 是抓取墊**平面**到軸心的距離；平面是一條弦，它的兩個角在 21/cos(25°) = 23.17 mm，實際包絡是 Ø46.35。單臂內的檢查全綠（同一臂上沒有相鄰的墊），只有跨臂那組會紅——而跨臂那組是後來才補的。沒補的話這個穿模會一路帶進實體列印，而每一個既有的綠勾都不會有異狀。
- **如何預防**：① 包絡半徑一律由最遠頂點算出，成為一個具名的量（envelope），不要讓間距不變式直接讀標稱尺寸；② 間距檢查對 envelope 而非對 nominal；③ 非圓形零件的「直徑」欄位在文件裡要標明它指的是面還是角。

### 代理測試如果測的是一個不存在的組態，綠燈與紅燈都不帶資訊
- **觸發情境**：想驗的東西不好直接量，於是拿一個「差不多」的組態當代理——把末端件對自己的複本比、拿相鄰件當替身、用簡化模型代替真件。
- **該主動檢查**：這個代理**在成品裡真的存在嗎**？問一句「如果這條斷言翻紅，我會知道成品的哪一件事出錯」。答不出來，那條斷言就沒有涵蓋任何東西。
- **為什麼沒抓到**：綠燈的外觀不會告訴你它守的是什麼。本輪拿指尖去對「接在它上面的另一個指尖」掃掠——但成品裡指尖上面不接東西。關節軸方向改動前它剛好綠（勾爪恰好指向讓開的方向），改動後它紅了 115 個重疊；**兩次都與真實幾何無關**。更危險的是前者：一個永遠不會問到重點的斷言，在報表上和真正的守衛長得一模一樣。
- **如何預防**：① 每條斷言都要能回答「它翻紅代表成品的什麼壞了」；② 代理只在成品確實含有那個組態時才成立，否則換成一條能直接判定的不變式（本輪換成「指尖特徵不得越過本體中心平面」，機器擋得住且對應真實的下方關節）；③ 代理測試的涵蓋範圍要寫進文件的邊界段，不要讓後人把它當成完整覆蓋。

### 不改變包絡的特徵，尺寸量測對它是全盲的
- **觸發情境**：程式化建模／任何「在既有物件上加特徵」的產生器，而驗收靠尺寸讀回（bounding box、外形量測）。
- **該主動檢查**：這個特徵**會不會改變包絡**？不會的話，尺寸讀回對它就是盲的——改量一個會隨特徵變動的量（面數、體積、檔案雜湊）。還有：兩個**本來就該不同**的產出物，直接比它們彼此，而不是各自去比對期望值。
- **為什麼沒抓到**：兩層疊在一起。第一層，Blender 的 `hide_viewport` 會把物件移出 depsgraph，套在未評估物件上的 Boolean **靜默不生效、不報錯**。第二層，那些特徵（環孔座、勾爪）全部落在本體包絡之內，所以 STL 尺寸讀回 36 × 36 × 29.6 mm 完全正確，整份產出物契約十四項全綠。唯一的破綻是兩個檔案 byte 相同、面數都是 3436——而契約根本沒有比較這兩個檔案。
- **如何預防**：① 產生器加完特徵後自我檢查「面數必須增加」，不增加就 fail loud；② 驗收要選對該變更**敏感**的量，「全綠」只覆蓋量得到的維度；③ 對兩個應當不同的產出物加一條「必須不同」的斷言——「兩個都對」與「兩個是同一個東西」在各自的斷言下長得一模一樣。

### 連線旗標只記得「我方有沒有要關」，不知道對方已經走了
- **觸發情境**：服務以長連線持有下游（socket、DB pool、gRPC channel），而它的 health／readiness 是從一個**本機旗標**推導出來的，不是探測出來的。
- **該主動檢查**：親手製造「先連上、對方之後才退出」這個順序去看旗標——只測「一開始就連不上」會全過。再問一句：這個旗標的名字宣稱的是對端狀態，它讀的是哪一邊的變數？
- **為什麼沒抓到**：旗標在兩個相反的真實狀態下長得一模一樣。asyncio 的 `StreamWriter.is_closing()` 報的是我方意圖；對方送 FIN 之後 `eof_received()` 保留半關閉、transport 不會自己收，所以旗標永遠是 True。更隱蔽的是：**既有教訓寫著「健康端點誠實回報了 disconnected」**——那句話只在「API 後啟動、從沒連上」的順序下成立，反過來它會說謊。同一條教訓的另外半邊從來沒被涵蓋，於是後續所有引用它的人都繼承了那個未言明的前提。
- **如何預防**：① 連線旗標必須納入對端訊號（EOF、keepalive、探測），只讀我方狀態的旗標不得對外宣稱是 readiness；② health 的每個斷言都要有 should-fire 與 should-pass 一對，且 should-fire **必須用「連上後對方離開」的順序**製造，不能用「從沒連上」代打；③ 讀到教訓裡「當時 X 是誠實的」這種敘述，先問「在別的啟動順序下還誠實嗎」——把它當待驗項，不是已知事實。

### 重啟被依賴的服務，不等於依賴它的那一端也回復了
- **觸發情境**：只重啟拓撲中的一個服務（引擎、資料庫、broker），而上游持有的是啟動時建立、不會自動重連的長連線。
- **該主動檢查**：誰在**啟動時**握了這條連線？重啟被依賴方之後，**上游是否也重啟過**？用一個會真的走完那條連線的請求去驗，不要只看單一服務的狀態。
- **為什麼沒抓到**：健康端點誠實回報了 `blender: disconnected`，但沒有人去讀它——而資料路徑上的失敗**偽裝成別的錯誤**：死掉的 socket 送出後收到空回應，於是變成「回傳的場景資訊缺少欄位」（422），而不是「引擎連不上」（503）。看到 422 的人會去查資料格式，不會去查連線。
- **如何預防**：① 單一服務的安裝／重啟目標，必須連同重建它的相依方（本專案：`install.sh blender` 現在會等 listener 就緒再重啟 API，與 `all` 同序）；② 死連線要能被辨識成連線失敗，而不是退化成內容錯誤——否則錯誤訊息會把人引到錯的方向；③ 重啟任何一環後的驗收，一律用**跨越該連線的端到端請求**，而不是各服務各自的狀態。

### 檔案系統同步服務會偽裝成 git、套件管理器與 agent 的錯誤
- **觸發情境**：專案位於會被雲端同步的目錄（macOS 的「桌面與文件」、Dropbox、OneDrive）。出現檔名帶「 2」的副本、0 bytes 的檔案、無法解釋的相依損壞，或不明高負載時。
- **該主動檢查**：先確認同步是否涵蓋這個專案——macOS 看 `ls -ld ~/Library/Mobile\ Documents/com~apple~CloudDocs/Desktop` 是否為指向 `~/Desktop` 的 symlink。再看 `ps aux | sort -rn -k3` 有沒有 `bird`／`cloudd`／`fileproviderd` 佔住 CPU。0 bytes 但邏輯大小非零的檔案是 dataless placeholder，是同步的指紋。
- **為什麼沒抓到**：每個症狀單獨看都像別的東西的錯——壞掉的 `refs/heads/main 2` 像 git 的問題，`node_modules` 裡建構子變成 object 像 npm 的問題，被掃進 commit 的 112 個副本像 agent 的問題。四者被當成四個獨立意外分別修掉，根因原封不動。
- **如何預防**：① 專案目錄不要放在同步範圍內，或至少排除 `.git`、`node_modules`、建置產物與暫存目錄；② 遇到上述指紋時**先驗環境再驗程式**；③ 高負載期間量到的逾時與效能數字一律不可信，先看是誰在吃 CPU；④ 相依損壞的確定性修法是依 lockfile 重裝（`npm ci`），但同步仍開著就會再發生。

### 閘門宣稱涵蓋的範圍，與它實際比對的集合，是兩個不同的東西
- **觸發情境**：任何以「名稱清單」界定偵測範圍的檢查器——型別名、關鍵字、副檔名、路徑前綴。它報 OK 時。
- **該主動檢查**：這個閘門的**掃描根目錄**涵蓋哪些樹？它比對的**名稱集合**是否包含同義的抽象型別或別名？兩者都要親自讀設定，不能看它印 OK 就當涵蓋。
- **為什麼沒抓到**：閘門對它讀不到的東西「零發現」，與真的乾淨長得一模一樣。此處是雙重的：`TARGET_TYPES` 只列字面的 `dict`/`list`，讓 `Mapping`／`Sequence` 的窄化整批繞過；而整個 `scripts/` 樹（含閘門自己的原始碼）根本不在任何 lint／型別／掃描的根目錄裡。閘門自己也沒有測試，所以沒有任何東西會質疑它的涵蓋範圍。
- **如何預防**：① 每個閘門都要有「範圍測試」——斷言它被以正確的根目錄呼叫（讀 CI 腳本本身）；② 名稱集合要涵蓋語意同義詞，不只字面拼寫，並用 should-fire fixture 逐一釘住；③ 閘門必須有 should-pass fixture，否則「永遠報錯」與「正常運作」無法區分；④ 同一族的閘門（lint／型別／自製掃描）**排除清單要一致**，範圍不一致會產生沒人能處理的發現。

### 分析器提早放棄產生的綠燈，與程式碼真的沒問題無法區分
- **觸發情境**：靜態分析工具（lint 規則、型別檢查器）對某檔案回報零問題。
- **該主動檢查**：這個檔案裡有沒有會讓分析器**中止該區段分析**的構造（自我引用、無法解析的符號、動態存取）？移除那個構造後，同樣的檢查是否仍然零問題？
- **為什麼沒抓到**：一個 `useCallback` 在宣告完成前引用自己，讓 react-hooks 規則停在該處；同一元件更下方的 ref-during-render 違規因此從未被回報。重構移除自我引用後，那個違規立刻出現——它一直都在。
- **如何預防**：把「重構後**新增**的告警」與「重構後**才被看見**的告警」分開判定：用改動前的原始碼跑一次同樣的檢查，才知道是誰造成的。不要因為「改完才紅」就假設是自己弄壞的，也不要因為「改前是綠的」就相信改前沒問題。

### 前綴選取是資料邊界；輔助物件共用前綴會改變受驗產品
- **觸發情境**：用名稱前綴、標籤或 selector 定義要匯出、分析或部署的物件集合，同一流程又產生展示、診斷或暫存物件。
- **該主動檢查**：產品集合與輔助集合的 selector 是否互斥？選取數是否等於契約明定數量，而不是只檢查結果非空？
- **為什麼沒抓到**：輔助物件本身合法且畫面正確，但寬鬆前綴也將它們納入產品分析；成功選取與 `review` 狀態都無法指出集合已被擴大。
- **如何預防**：先分配互斥命名空間，再以精確 expected-count 和禁止 issue/truncation 共同守門；展示物件不得繼承產品 selector。

### 屬性已改動，不等於派生世界狀態已同步
- **觸發情境**：建立、複製、移動或隱藏場景物件後，立刻用世界變換、評估網格或空間索引做匯出與幾何驗證。
- **該主動檢查**：派生狀態是否已在明確同步邊界後更新？用一個非零位移物件比對局部位置與世界座標，並由世界座標 oracle 檢查預期半徑或接觸。
- **為什麼沒抓到**：來源屬性會先顯示新值，依賴它的世界矩陣或評估資料仍可能是舊快取；只看畫面、來源欄位或成功匯出都能形成假綠。
- **如何預防**：把 scene/dependency-graph refresh 放在「完成一批變換 → 匯出／BVH／量測」的共用邊界；契約同時守中立間隙與位移後的止擋接觸，讓 stale world state fail loud。

- **該主動檢查**：卸載後是否有 bounded wait，確認 label 真正不可查才 bootstrap？bootstrap 失敗是否 bounded retry？完成後是否同時驗證 launchd state、PID listening port 與 health，而非只信其中一個訊號？
- **為什麼沒抓到**：把非同步 lifecycle 當同步操作，也把「舊 job 還存在」誤判為「新 job 已載入」。兩個瞬間狀態都不能證明最終服務存活。
- **如何預防**：installer 封裝 wait-for-unload 與 bounded bootstrap retry；最後以 label、port、health 三個獨立訊號驗證。部署測試鎖定 wait/retry helper，避免後續簡化腳本時復發。

### Operator 宣告 `UNDO` 不等於程式化呼叫真的推入可復原 transaction
- **觸發情境**：用 Python 自訂 Blender operator，`bl_options` 已含 `UNDO`，再由另一段 Python／socket 腳本呼叫它，便宣稱「一次呼叫＝一筆 Undo」。
- **該主動檢查**：operator 的**呼叫端**有沒有明確啟用 undo 執行參數？官方 `bpy.ops` 呼叫契約把 `execution_context` 與 `undo: bool` 列為獨立 positional arguments；遠端程式化呼叫要用 `bpy.ops.x.y('EXEC_DEFAULT', True)`，不能只讀 class metadata 推論 runtime stack。測試必須建立兩個 nonce 物件、一次變形、一次 Undo，再由獨立 oracle 確認兩者保留且 transform 全復原。
- **為什麼沒抓到**：單元測試只檢查 generated code 含 `bl_options={'UNDO'}`，變形結果也正確；表面證據同時相容於「有推 stack」與「沒有推 stack」。真機第一次 Undo 直接退回上一個 seed transaction、把 fixture 物件刪掉，才揭露呼叫預設未建立 batch undo step。
- **如何預防**：① 對程式化 Blender mutation 同時檢查 operator 宣告與呼叫參數；② 把 `('EXEC_DEFAULT', True)` 做成 codegen 單元 sentinel；③ 真機 gate 用「一次 Undo 復原多個既存物件」的鑑別性斷言，不能只看 `/api/undo` 回 success。

### 傳入 allowlist 不等於 guard 已啟用；安全選項的「資料」與「機制開關」要分開驗
- **觸發情境**：第三方 server/middleware API 同時接受 `allowed_hosts`、`allowed_origins` 等 allowlist，另有一個獨立的 protection mode/enable flag。看到 allowlist 已傳入，就直覺認為 request guard 已生效。
- **該主動檢查**：送一個明確不在 allowlist 的 Host/Origin，真的拿到 403 嗎？本輪 FastMCP 3.4 的 `allowed_*` 只是 guard 的參數，`host_origin_protection` 預設仍可為 false；資料存在但機制沒 mount，惡意 Origin 照樣 200。協定版本亦同：initialize 本身用 params 協商版本，不是驗證後續 request header 的鑑別點；要用 `tools/list` 帶錯誤 `MCP-Protocol-Version` 才會真正觸發 400。
- **為什麼沒抓到**：把「設定物件看起來完整」當成 runtime behavior；單看 source/config 會得到假綠。initialize 又是特例，用它測 header 讓測試本身失去鑑別力。
- **如何預防**：安全設定一律加 negative request sentinel：不可信 Origin→403、未支援 protocol header（非 initialize request）→400、缺 identity→401。先觀察 sentinel 在 guard 缺席時確實紅，再補 enable flag；禁止只 assertion config 文字或 constructor kwargs。

### 改了 plist env 卻「kickstart 重啟」→ 沒生效：kickstart 不 reload、載入的是另一份拷貝
- **觸發情境**：改了 launchd plist 的環境變數（CORS、feature flag、port…）然後「重啟服務」想讓它生效。
- **該主動檢查**：你的「重啟」真的 **reload 了 plist** 嗎？`launchctl kickstart -k` 只重啟**進程**、不重讀 plist；而且**載入中的 plist 往往是 `~/Library/LaunchAgents/` 的另一份拷貝**，不是你剛編輯的 repo/deploy 那份。驗證要讀「載入中進程的實際 env」——`launchctl print <domain>/<label>`，不是讀你剛改的檔。
- **為什麼沒抓到**：本輪我改了 `deploy/launchd/*.plist` + `kickstart`，宣稱「已部署＋已驗證」。但 kickstart 沒 reload、載入的是舊拷貝，env 根本沒變。更糟的是驗證**不夠鑑別**：我只測了一個「新舊設定都會擋」的 case（CORS Origin=19504，在舊的 [tailscale,19147] 與新的 [tailscale-only] 下**都**被擋），於是假綠，直到下一輪查別的才撞見。同族：本 session 一路的「表面訊號≠真實、驗證要鑑別性」。

### `narrow(x) or default` 把「畸形」訊號連同「空」一起塌掉——正確用了 SSOT，尾巴一個 `or {}` 又是 silent-fallback
- **觸發情境**：一個收窄／解析函式以 `None`（或空）表示「輸入畸形／不符預期」，呼叫端寫成 `narrow(x) or default`（`as_str_keyed(o) or {}`、`parse(s) or []`、`.get(k) or fallback`）。尤其在剛把某個 bug class 改成「一律走 narrowing SSOT」之後——會覺得「用了 SSOT 就安全了」。
- **該主動檢查**：`narrow` 回 `None` 的**語意**是什麼？若它同時代表「合法的空」與「畸形輸入」兩種情況，`or default` 就把兩者**塌成同一個值、且無聲**——呼叫端從此分不出「addon 回了 list/null」和「場景本來就空」。問：畸形這條路徑有沒有留下**可觀測**的痕跡（log/raise/metric）？
- **為什麼沒抓到**：`or default` 讀起來像無害的 defaulting，而且**它前面確實用了正確的 narrowing 工具**，所以 review 和 CI（mypy、container-narrowing gate）全綠——那些 gate 檢查「有沒有收窄」，不檢查「收窄失敗後有沒有靜默吞掉」。本輪 `get_scene_info` 就是：`as_str_keyed(...) or {}`，`as_str_keyed` 只在非字串 key 時警告，非 mapping 時回 `None` → `or {}` 靜默成 `{}`。與 07-15『health/靜默退化成空』、NO_SILENT_FALLBACK 同族。
- **如何預防**：收窄失敗要**明確分支**、留痕再回退：`n = narrow(x); if n is None: logger.warning(...); return default; return n`——別用 `or default` 把 `None` 一步吞掉。把「畸形 → 有 log / raise」當契約，並為它寫一個「餵畸形輸入、斷言有 warning」的測試（本輪這條測試正是抓到 bug 的那個）。延伸：**搶救「不是我建、即將丟棄」的 commit 前，先查它是否含 main 沒有的測試覆蓋**——那些測試可能正守著一個 main 已違反的契約（本 bug 就是併入被搶救的測試時當場 fail 才暴露的）。

### 純函式的「層」由它承載的知識決定，不由它的形狀（純度）決定
- **觸發情境**：一個 helper 看起來像 domain（純函式、無 I/O、只做資料轉換），但它**編碼了某個特定 backend 的知識**（某 addon 只吃哪些指令、產出某引擎的方言／DSL／SQL 方言／bpy 程式碼）。決定它放哪一層時。
- **該主動檢查**：這個函式**知道什麼**？若它知道「某個具體外部系統的限制或方言」，它屬 adapters 層，**不管它多純**。反問：domain 或 use case 匯入它，會不會就等於讓核心層知道了某個 addon/DB/引擎的存在？會＝放錯層。
- **為什麼沒抓到**：「純函式」直覺上很想放進 domain/use_case（無副作用、好測）。但純度是**機械性質**，跟**知識歸屬**無關。放進 use case 後，每條 dispatch 路徑都得自己記得呼叫它（本輪的 chokepoint bug 正是這樣長出來的：翻譯知識放在 use case，第二條 use case 忘了呼叫）。而且它一旦想下沉到唯一必經層（adapter），就會發現 domain/use_case→adapter 是反向匯入、動不了——放錯層在架構上是會「卡住」的。
- **如何預防**：放層看**知識**不看**純度**。backend-specific 的純函式（codegen/方言轉換/協定 quirk）放進該 backend 的 adapter，讓它成為那條路徑的唯一必經點；核心層只說領域語言，由 adapter 翻譯成方言。本輪：把 `blender_tool_codegen`（產 bpy code）從 `use_cases/` 移到 `adapters/mcp/`，翻譯下沉到 `BlenderMCPAdapter._dispatch`（execute+call_tool 都必經），最內層 `BlenderMCPClient` 對「仍是高階工具＝有人繞過」大聲失敗（runtime sentinel）——上一條『自稱唯一入口若無機制強制』的處方就此**機制化落地**（真 Blender 驗證：高階 create_object 過真 adapter 後 addon 回 exists＋8 頂點）。

### 部分 gate 給的是假覆蓋率：綠勾只涵蓋被跑到的子集，沒跑到的測試會靜默腐爛
- **觸發情境**：一個測試/檢查存在於 repo，但 CI 的 runner 只跑其中一部分（例：`pytest tests/unit`，而 `tests/e2e` 從不被跑）。任何時候看到「gate 只指向一個子目錄／一個標籤／一組檔案」都要警覺。
- **該主動檢查**：這個 gate 的涵蓋範圍，和「repo 裡實際存在的同類檢查全集」對得起來嗎？有沒有測試檔**存在但從不被任何 gate 執行**？綠燈是「全部通過」還是「被跑到的那些通過」？
- **為什麼沒抓到**：綠勾同時相容於「測試都過」與「有測試根本沒跑」——和 07-17『型別檢查器報綠≠有在檢查』、以及 health『訊號說的比它守的多』同族。本輪一個 e2e 斷言在產品行為正確變更後過期變紅，紅了一個月沒人知，正因為 `tests/e2e` 不在 gate 內；它是被『補一個新測試、順手擴大跑 e2e』意外撞見的，不是被機制抓到的。
- **如何預防**：gate 的涵蓋範圍要嘛是「全集」（跑整個 test root，而非某子目錄），要嘛對「刻意排除的部分」有顯式清單＋理由（一如 `# type: ignore`／deferral 要理由）。新增一批測試時，同時確認它落在被 gate 執行的路徑內——否則就是寫了個永遠不會 fail-loud 的測試。排除某些測試（需真硬體等）是合法的，但排除本身要可見、可 review，不能是「runner 剛好沒指到那裡」的沉默預設。

### 自稱「唯一入口 / single chokepoint」的宣稱若無機制強制，新增一條路徑就會靜默繞過它
- **觸發情境**：某個轉換／守衛／正規化被設計成「所有 X 都必須經過的單一收斂點」（docstring 或命名這樣寫），而呼叫它是**各呼叫端自律**、不是型別或架構強制。尤其當同一種操作有**多條 dispatch 路徑**時。
- **該主動檢查**：這個「唯一入口」實際被呼叫了幾次、在哪幾條路徑？把「所有會做這種 dispatch 的路徑」列全，逐條確認它們**都**經過那個收斂點——別信 docstring 的宣稱，用 grep 把呼叫點數出來。宣稱（claim）與強制（enforcement）是兩回事。
- **為什麼沒抓到**：宣稱寫在註解裡，沒有任何東西讓「繞過它」變成編譯錯或測試紅。第一條路徑正確接上後，收斂點看起來「就位了」；第二條路徑（可能後來才加、或本來就存在但沒人對照）直接 dispatch，型別檢查照過、單元測試各自 mock 掉真實下游也照過。本輪：一個把高階工具改寫成底層呼叫的 `translate` 自稱 single chokepoint，實際只有一條 use case 路徑用它，另一條生產 pipeline 路徑直送未翻譯的呼叫給只認底層工具的下游——與 07-17『同 class 只修了人看到那處』、checking-claims-are-enforced（宣稱≠強制）同族。
- **如何預防**：真要「單一入口」就用機制強制，不要靠自律——把收斂點下沉到**所有路徑都必經的那一層**（例：dispatch 的最底層 adapter），或用型別讓「未經收斂的值」無法被 dispatch（newtype / 只有收斂點能產出的型別）。若因為下游會變（不同 adapter 對應不同能力）而無法下沉，那它本來就不是 single chokepoint——就別這樣宣稱，並為每條路徑各自加一個「有沒有經過收斂」的哨兵測試。

### 「debrief 點名了」不等於「程式碼修掉了」：一個 bug class 的防線若不進 CI，人肉巡檢就會漏
- **觸發情境**：把一個 bug class 的殘留清乾淨後，靠「手動 grep + 記在 LESSONS」當防線。承前一筆——那筆 debrief 明確**點名** `blender_mcp_adapter.get_scene_info` 是存活實例之一。
- **該主動檢查**：被 debrief 點名的每個實例，程式碼裡**真的改了嗎**？別把「已記錄」當「已修復」。本輪 `reveal_type` 實測：`get_scene_info` 直到今天仍回 `dict[Any,Any]`（fix 當時落在同檔另一個方法 `_decode_response`，被點名的那個方法沒動）——在 mypy --strict 全綠下又活了一天。
- **為什麼沒抓到**：唯一防線是「手動 grep `isinstance(.*, dict)`」＋人的記憶，兩者都沒有到期日、沒有 fail-loud。名字寫進文件不會讓 CI 變紅；下一個人（或 subagent）照抄髒 pattern 時，沒有任何東西擋。
- **如何預防**：把這個 class 做成**可執行 gate 進 CI**，別靠巡檢。做法採 **checker-first／顯式豁免**：gate 找出每個真實 `isinstance(_, dict|list)`（`dict[Any,Any]` 與 `list[Any]` 同樣靜音；用 AST，不誤配字串/註解裡的字面），除非①位於 narrowing SSOT 定義檔、②該處帶 `# narrow-ok: <理由>`（必須有非空理由，一如專案對 `# type: ignore` 的要求），否則 fail。**不要**讓 gate 去「自動判斷某處誠不誠實」——誠實只有 `reveal_type` 在取值點才證得出，CI 做不到；gate 若自作聰明判斷，就又是一個對這個 class 天生瞎的工具（重蹈 07-17→07-18 的覆轍）。gate 的職責是把整個 class **從沉默變可見、可 review**，不是證明誠實。本專案落地：`scripts/check_container_narrowing.py`，接在 `scripts/ci.sh` T1 mypy 之後。

### 「用檢查器列出同 class 全部實例」有個盲區：檢查器對第三方/`Any` 邊界結構性看不到 → 那個子類要用 grep
- **觸發情境**：清一個 bug class 的殘留（承 2026-07-17「同 class 只修了人看到那處」）。其中有些實例的值源自**未定型第三方 SDK 或宣告成 `object` 的欄位**——`isinstance(x, dict)` 後直接用／直接回傳。
- **該主動檢查**：這個 class 的實例裡，**哪些檢查器根本沉默**？值一旦退化成 `Any`（lazy-import 的未定型套件、`--ignore-missing-imports`、`object` 欄位經 `isinstance` 只到 `dict[Any,Any]`），檢查器對它零報錯＝零線索。這種子類**不能靠檢查器盤點**，要用結構性 grep：`isinstance(.*, dict)`、餵給 `open(`/`dict[str,object]` 回傳的 SDK 取值點。
- **為什麼沒抓到**：2026-07-17 的處方是「用檢查器去問其餘實例」——對 union/可空型別成立，但對「檢查器被 `Any` 蒙眼」的那一半實例**恰好失效**：你拿一個對這些實例天生瞎的工具去盤點，回報「乾淨」。本輪就有兩個殘留（`hunyuan3d_adapter` 直接 `open(Any)`、`blender_mcp_adapter.get_scene_info` 把 `dict[Any,Any]` 當 `dict[str,object]` 回傳）在 mypy --strict 全綠下存活。
- **如何預防**：① 盤點一個 bug class 時先分流——「檢查器看得到的」用檢查器、「值會退化成 `Any` 的邊界」用 grep，兩條都要跑，不可只信檢查器的綠燈；② 抽出防腐層 helper（本專案的 `src/infrastructure/narrowing.py`）那一刻，**同批掃完所有既有邊界**改用它，別只轉換觸發它誕生的那一處——否則未遷移的邊界就是這個 class 的下一批溫床（narrowing 誕生於 07-17，這兩處當時沒一起遷）。

## 2026-07-17

### 型別檢查器報綠 ≠ 它有在檢查：`Any` 是靜音區，零錯誤可能是零檢查
- **觸發情境**：為了讓型別檢查器過而做收窄／抑制（`isinstance`、`# type: ignore`、放寬成 `Any`）；或在 JSON／外部 API／未定型第三方套件的邊界標型別。把型別檢查升成 hard gate 之前尤其要問。
- **該主動檢查**：收窄之後的取值點，型別**實際**是什麼？`isinstance(x, dict)` 執行期無法檢查型別參數，只能收窄成 `dict[Any, Any]`——於是後面整條 `.get()` 鏈都是 `Any`，檢查器全程沉默卻報 Success。既有的每個 `# type: ignore` 是否正遮著一個真 bug？
- **為什麼沒抓到**：檢查器對 `Any` **不報錯**，所以綠燈同時相容於「都對」與「都沒看」。肉眼讀程式碼分不出這兩者——`x.get(a).get(b)` 看起來跟有檢查的版本一模一樣。抑制手段沒有到期日，壓下去就永遠沉默，且下一個人會當成既有慣例照抄（本輪就發生：subagent 忠實照抄了既有的洞，而那個「參考範例」是我指給它的）。
- **如何預防**：① 收窄後每一跳**明確重新標註回 `object`**（不是 `Any`），逼出下一個 isinstance——沒有這個標註，`.get()` 就回 `Any`、後面全盤失守；② 判斷修法誠不誠實的**唯一**方法是在關鍵取值點插 `reveal_type` 確認它**不是 `Any`**，這件事不能靠讀 code 判斷；③ 升 hard gate 前先抽查幾個外部資料邊界，確認綠燈不是盲區換來的；④ 每個 `# type: ignore` 必須附「為什麼安全」，否則視為**待驗 bug** 而非既成事實。

### 同 class 的 bug 只修了「人剛好看到的那處」——因為檢查器在另一處被 `Any` 蒙住眼
- **觸發情境**：修一個「值的形狀不如預期」的 bug（union 成員、可空、多型回應、外部 API 回傳）時，同一個 class 在 repo 別處還有實例。
- **該主動檢查**：這個 bug class 還有哪些實例？要用**檢查器**去問，而不是靠 grep 或記憶。若某處檢查器沉默，先問「它是不是被 `Any` 蒙住了」，而不是當成那處沒問題。
- **為什麼沒抓到**：前一筆 commit 修了 A 檔的 `content[0].text`（union 首元素不一定是該型別），**同一筆 commit 就改到 B 檔**，但 B 檔同一個 bug 活下來——因為那裡的呼叫匹配不到 SDK overload → 回傳退化成 `Any` → 檢查器無法指出。人只修了自己肉眼掃到的那處，並合理地以為修完了。**同檔內甚至自相矛盾**：另一個方法正確地做了型別過濾，錯的那處就在它上面幾十行。
- **如何預防**：修完一個 bug class，把「檢查器能否列出其餘實例」當成收尾條件；檢查器在某處沉默＝那處的型別要先修好，它不是清白證明。跨檔案同 class 掃描要問「哪裡的型別資訊被抹掉了」，而不只是 grep 同樣的字面寫法。

### 教訓落了檔、處方沒進 gate → 同一個洞繼續長出新 bug
- **觸發情境**：上一輪 debrief 開了預防處方（「每個 X 入口點都該有 Y 測試」），但沒有任何機器在檢查它有沒有被實作。
- **該主動檢查**：上次開的處方**實際兌現了嗎**？有機器 gate 在守嗎？動工修 bug 前先查同 class 教訓（consult-first），命中就先看處方是否已實作——沒實作的處方就是這個 bug 的溫床。
- **為什麼沒抓到**：LESSONS_LEARNED 是**文件不是 gate**。寫下「應該要有 smoke test」不會生出 smoke test；文件被寫下的那刻感覺像問題解決了，其實只是被記錄了。本輪的真 bug 正好長在上一輪明文指出「這裡缺測試」卻沒補的那個函式裡。
- **如何預防**：處方必須落成**可執行的 check**（測試／lint／CI gate），否則明確標成 TODO 並排程；debrief 收尾時回頭確認上一條同族教訓的處方是否已兌現，未兌現就當本輪的待辦，不要再寫一次一樣的話。

### 測試替身的攔截目標寫死 → 靜默 fallthrough，真依賴漏進「隔離」測試
- **觸發情境**：用 mock/stub/service-worker（MSW、nock、VCR…）攔截網路以做隔離測試時，攔截規則裡出現具體 host/port/URL。
- **該主動檢查**：攔截 URL **是否從執行期環境推導**（`location` 等）、並與**受測程式的 URL 推導邏輯逐字對齊**？跑測試時，是否有**觀測得到的判別**證明攔截真的生效（而非只看到「mock enabled」的 log）？
- **為什麼沒抓到**：攔截比對不到時多半**不報錯**——請求直接走真網路。於是「mock 開著」與「mock 生效」被混為一談；更陰險的是**只有在真依賴剛好活著時才看得出來**（真依賴沒開時，失敗看起來就像普通連線失敗）。
- **如何預防**：① 攔截 URL 一律推導、永不寫死；② 每個隔離測試先跑**隔離自檢**——挑一個「只有真依賴會產生、fixture 絕不會產生」的可觀測特徵，斷言它**不存在**（例：dummy run 的預覽必須是 fixture 圖，出現真實視窗＝漏水）。同族：`表面成功訊號≠語意真實`（下一條）——都是「訊號在說謊」。

### 表面成功訊號 ≠ 語意真實（驗證必須用獨立 oracle + 鑑別性斷言）
- **觸發情境**：要證明「某條管線/整合真的在作用」時（尤其牽涉外部系統：DB、Blender、裝置、第三方服務）。
- **該主動檢查**：用一條**與受測系統的資料路徑物理獨立**的通道讀 ground truth，並讓斷言帶**只有真系統才產得出的鑑別特徵**（隨機 nonce、精確幾何/數值、狀態差分），而不是只看「有回應/有畫面/200 OK」。
- **為什麼沒抓到**：表面訊號會騙人——一個壞掉、斷線、甚至假的後端也能回 200、也能讓前端畫出一個方塊。缺的是「這訊號只有真系統在跑才可能出現嗎？」這一問。
- **如何預防**：驗證計畫先做 falsifiability 過濾（「假後端還會過嗎？會過就剔除」）；至少一個獨立 oracle + 一個非空 ground-truth 差分斷言。範例：Blender 管線用直連 socket `execute_code print(len(bpy.data.objects))` 當 oracle，斷言 nonce 物件的頂點數==8。

### health/status 訊號與其宣稱守護的相依性脫鉤
- **觸發情境**：一個服務有 `/health` 或就緒訊號，而它其實依賴另一個下游（DB、引擎、外部程序）。
- **該主動檢查**：health 是否**實際探測**它所守護的相依性，還是硬回成功？消費者（watchdog、前端徽章、驗證腳本）是否誤把「服務活著」當成「整條鏈就緒」？
- **為什麼沒抓到**：硬回 `ok` 的 health 永遠綠，於是「healthy」不代表下游可用；驗證若信它就假綠。同族：靜默退化成空/placeholder（不報錯），讓斷線與空狀態不可辨。
- **如何預防**：health 反映真實相依（探測或連線 flag），且用一個不同的 status 維度表達下游（例：`status:ok` 表本服務、`blender:connected/disconnected` 表引擎）；驗證絕不把 health 當下游就緒的證據。

### 入口點宣告了執行環境不會注入的相依 → runtime 首次連線才爆
- **觸發情境**：新增/修改框架路由 handler（HTTP / WebSocket / event handler），其參數靠框架依賴注入。
- **該主動檢查**：這個 route type 的執行環境**真的會提供**你宣告的每個參數型別嗎？（例：WebSocket route 不會有 HTTP Request）。有沒有一個 smoke test 真的去打這個入口點、斷言它不 crash？
- **為什麼沒抓到**：型別檢查/import 都過，錯誤延到「首次有連線進來」才 raise，且訊息指向表面（`missing 1 required positional argument`）而非根因（此 route 不注入該型別）。單元測試沒有真的 open 這個 endpoint。
- **如何預防**：每個 WS/事件入口點配一個「連上→送一則→不 crash」的 smoke test，進 release-readiness Lane A（機器可重複 gate），別靠使用者當測試員。

### 部署產物硬編值與配置 SSOT 漂移
- **觸發情境**：launchd plist / Dockerfile / systemd unit 等部署產物裡硬編了 port/path/label，而這些值另有 SSOT（如 services.yaml）。
- **該主動檢查**：部署產物內的硬編值是否與 SSOT 逐項對齊？重啟服務會不會因產物漂移而把它換到沒人用的 port？
- **為什麼沒抓到**：產物平時不被執行（服務可能由別的機制起在對的 port），漂移潛伏；一旦真的用該產物重啟就爆。sentinel 只檢查了 path 沒檢查 port。
- **如何預防**：sentinel 交叉比對部署產物的關鍵值 vs SSOT（不只 path，含 port/label）；產物盡量從 SSOT 生成或用 placeholder 替換，別硬編。
